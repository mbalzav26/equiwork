# 5.6.1 Patrón de diseño

Para definir y describir la arquitectura de un sistema de software suelen emplearse métodos complementarios: (1) **vistas arquitectónicas**, que separan la lógica funcional (componentes y capas), la distribución física (servidor, base de datos, cliente), el flujo de procesos (petición–respuesta) y, cuando aplica, el despliegue; (2) **modelado gráfico**, mediante diagramas UML (casos de uso, clases, secuencia, actividad) y diagramas de estructura (mapa del sitio, modelo relacional, wireframes), que fijan el vocabulario común entre analistas y desarrolladores; (3) **documentación estructurada** del diccionario de datos, reglas de integridad y restricciones de seguridad; y (4) **patrones arquitectónicos explícitos** (por ejemplo capas, cliente–servidor o MVC), que orientan la organización del código y las dependencias entre módulos. En conjunto, estos métodos permiten describir qué hace el sistema, cómo se descompone y cómo interactúan sus partes sin depender solo del código fuente.

EquiWork adopta una **arquitectura en capas** (multinivel) sobre el patrón **cliente–servidor**: el navegador consume páginas web (EJS) y la API REST `/api`, mientras un único servidor Node.js concentra la lógica. La organización interna sigue una variante de **MVC ampliada**: las **rutas** (`webRoutes`, `apiRoutes`) enrutan las peticiones; los **controladores** adaptan HTTP y delegan en **servicios**, donde reside la lógica de negocio y las validaciones; los **repositorios** encapsulan el acceso a datos con Sequelize; y los **modelos** representan las entidades persistentes. Middlewares transversales (autenticación JWT, validación de entrada, manejo de errores) cruzan las capas sin mezclar responsabilidades. La capa de **presentación** incluye vistas EJS, assets en `public/` y JavaScript del cliente para dashboard, formularios y reportes.

La arquitectura del proyecto se **describe** mediante los artefactos elaborados en el diseño: diagramas de casos de uso y secuencia por funcionalidad, diagrama de clases de dominio, mapa del sitio, wireframes de interfaz, modelo relacional y diccionario de datos. Esa documentación, alineada con la estructura real de carpetas (`routes`, `controllers`, `services`, `repositories`, `models`, `views`), evidencia un diseño **monolítico modular**: un solo despliegue, pero con fronteras claras entre presentación, aplicación, dominio y persistencia, facilitando mantenimiento, pruebas y evolución hacia entornos productivos (por ejemplo MySQL en lugar de SQLite) sin rediseñar la arquitectura lógica.
